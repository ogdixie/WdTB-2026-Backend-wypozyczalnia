P1 · Zapytanie pochodne przez relację

Spring Data buduje zapytanie z nazwy metody; podkreślnik przechodzi przez relację.

// rezerwacje gościa o podanym nazwisku, od najnowszej
List<Reservation> findByGuest_FullNameOrderByStartsAtDesc(String fullName);

Jak czytać nazwę: findBy + warunek + opcjonalnie OrderBy…. Każdy kawałek to nazwa pola encji z wielkiej litery; parametry metody wypełniają warunki w tej samej kolejności.

Literówka w nazwie pola zatrzymuje start aplikacji z komunikatem No property … found for type …. Dokumentacja Spring Data JPA: tworzenie zapytań z nazwy metody (tabela wszystkich słów kluczowych), przejście przez relację, lista słów kluczowych.

P2 · JPQL z JOIN

Zapytanie piszecie sami w adnotacji @Query. JPQL używa encji i pól (Reservation r, r.table), nie tabel i kolumn, a join przechodzi przez pole relacji. Parametry to :nazwa w zapytaniu i @Param("nazwa") przy parametrze metody.

Najprostsze: jeden join i warunek na tabeli połączonej.

// w ReservationRepository: rezerwacje przy stolikach w podanej sali
@Query("select r from Reservation r join r.table t where t.room = :room")
List<Reservation> inRoom(@Param("room") String room);

Typowe P2: wynik z „drugiej strony” relacji. Szukacie stolików, a warunek dotyczy ich rezerwacji. Nadal jeden join, do tego distinct, bo stolik z kilkoma pasującymi rezerwacjami ma się pojawić raz. Takiego pytania nie zapiszecie nazwą metody w repozytorium stolików.

// w CafeTableRepository: stoliki, które mają co najmniej jedną rezerwację o podanym statusie; każdy raz
@Query("""
        select distinct t
        from Reservation r join r.table t
        where r.status = :status
        """)
List<CafeTable> tablesWithStatus(@Param("status") ReservationStatus status);

Dokumentacja: adnotacja @Query, parametry nazwane.

P3 · Zestawienie GROUP BY

Zestawienie nie zwraca wierszy tabeli, tylko policzone wartości, np. „stolik 2: 2 rezerwacje, 40 zł zaliczek”. Takiego wyniku nie da się zapisać w encji Reservation, bo encja to cały wiersz tabeli. Dlatego metoda zwraca projekcję: własny interfejs opisujący kształt jednego wiersza wyniku. Ma same gettery, a Spring Data wypełnia je wartościami kolumn o tych samych nazwach, co aliasy po as w zapytaniu (as tableNumber → getTableNumber()). Nie piszecie klasy ani implementacji, tylko interfejs.

Metoda zwracaCo to jestNa P3
List<Reservation>całe wiersze tabeli (encje)nie
List<Object[]>wartości bez nazw: row[0], row[1]…nie
List<TableLoad>projekcja: nazwane wartości getTableNumber(), getReservations()…tak

Na ocenę 4 wystarczy wariant najprostszy (jedna tabela, count). Sugestia P3 z Waszego pliku pytań to zwykle wersja ambitniejsza, z join i sum albo avg. Możecie ją uprościć do pytania, które daje się zapisać najprostszym wariantem.

Najprostsze: jedna tabela, grupowanie po kolumnie i count. Projekcja ma dwa gettery: grupę i liczbę.

// ile rezerwacji jest w każdym statusie (NEW: 2, CONFIRMED: 1…)
@Query("select r.status as status, count(r) as reservations from Reservation r group by r.status")
List<StatusCount> countByStatus();

public interface StatusCount {
    ReservationStatus getStatus();
    long getReservations();
}

Bardziej zaawansowane: grupowanie po kolumnie tabeli połączonej przez join, kilka wartości (count i sum) i sortowanie po wyniku.

// dla każdego stolika: numer, liczba rezerwacji, suma zaliczek
@Query("""
        select t.number as tableNumber, count(r) as reservations, sum(r.deposit) as deposits
        from Reservation r join r.table t
        group by t.number
        order by sum(r.deposit) desc
        """)
List<TableLoad> tableLoad();

public interface TableLoad {
    Integer getTableNumber();
    long getReservations();
    BigDecimal getDeposits();
}

Typ gettera musi pasować do tego, co zwraca funkcja w zapytaniu. Inaczej aplikacja zatrzymuje się z błędem konwersji.

W zapytaniuTyp gettera w projekcji
count(…)long
avg(…)Double
sum(…) po polu Integer / LongLong
sum(…) po polu BigDecimalBigDecimal
sum(…) po polu DoubleDouble
kolumna z group bytyp pola w encji, np. String, enum

Dokumentacja: projekcje (interfejsy z getterami).

ZadanieC · Test pytania

Każde pytanie ma własną klasę testową. Nazwa: numer pytania i nazwa repozytorium, np. P1ReservationRepositoryTest. Miejsce: ten sam pakiet co repozytorium, ale w src/test/java zamiast src/main/java. Dokładne ścieżki dla Waszych pytań są w pliku pytań, w tabeli „Gdzie to piszecie”. Przykład kawiarni:

PytanieMetoda wTest w
P1src/main/java/pl/wsb/kawiarnia/booking/repository/ReservationRepository.javasrc/test/java/pl/wsb/kawiarnia/booking/repository/P1ReservationRepositoryTest.java
P2src/main/java/pl/wsb/kawiarnia/seating/repository/CafeTableRepository.javasrc/test/java/pl/wsb/kawiarnia/seating/repository/P2CafeTableRepositoryTest.java

W IntelliJ: prawy przycisk na src/test/java → New → Package (nazwa jak pakiet repozytorium), potem w pakiecie New → Java Class. @DisplayName zaczyna się od numeru pytania: po nim reguła znajduje test. @DataJpaTest uruchamia czystą bazę H2 z danymi z data.sql.

// src/test/java/pl/wsb/kawiarnia/booking/repository/P1ReservationRepositoryTest.java
@DataJpaTest
class P1ReservationRepositoryTest {

    @Autowired
    private ReservationRepository reservations;

    @Test
    @DisplayName("P1 Rezerwacje gościa o podanym imieniu i nazwisku, od najnowszej")
    void p1ReservationsOfGuest() {
        List<Reservation> found = reservations.findByGuest_FullNameOrderByStartsAtDesc("Anna Kowalska");

        // oczekiwany wynik policzcie ręcznie z Waszych danych
        assertThat(found).hasSize(2);
    }
}

Dodatkowe dane tylko dla testu (gdy w data.sql brakuje ciekawego przypadku): plik src/test/resources/sql/p1.sql z poleceniami insert bez kolumny id i adnotacja @Sql("/sql/p1.sql") przy teście. data.sql zostaje bez zmian.
